## 2. Proposed checkpoint: existing support versus NEW behavior

Existing building blocks remain `queueFor(cwd)`, `enqueue(queue, topics, options)`, `runTrain({file,canonical,identity,main,prepare,validation})`, `guardPromotionJob(job)`, `withPromotionGuard(...)`, `withPromotionGuards(lanes, operation)`, `captureCompletionMember({canonical,identity,job,prepared,excluded})`, `validateTree(...)`, `verifyTrainResult(result,{project,saved})`, `completionFingerprint(state,id)`, `completionEvents(state,events,plan,org)` and `reconcileBatchCompletion({project,jobs,results})`. None currently implements the complete proposal. Manual `reconcile prepare|finish|refresh` stays unchanged and cannot accept these archived aliases. [S1–S7, S10]

Propose these **NEW interfaces**, implemented only after review, within existing foreground/native modules:

- `enqueueValidationCohort(queue, {manifest})`: validate all members/producer/authority, atomically reserve the complete cohort and its fixed ordering; never enqueue individually runnable member jobs. Duplicate identical manifests return the same checkpoint; changed inputs refuse.
- `advanceValidationCheckpoint({file, project, action, reportFile})`: finite explicit actions `prepare`, `gate`, `finish`. Prepare captures/replays/freezes; gate spends the one authorization and returns; finish verifies the producer transition and advances only evidence/bookkeeping. It never polls, dispatches a model, retries the gate or silently changes a candidate.
- `validateTree({...existingArguments, once: {attemptId, frozenDigest, consumedPath}})`: checkpoint-only execution contract, bypassing unrelated cache hits and verifying the outer native operation's consumed binding plus a create-exclusive inner-run entry. The outer operation consumes before host/profile preparation; only that fresh invocation may start its host child. Existing callers retain their guards and behavior. No new wrapper or alternate executor is introduced.
- A NEW checkpoint-specific report-intake validator, called inside the ordinary record transaction before storing/appending a frozen producer report, verifies the current claim and real bound execution/result. It does not confer authority through `ORG_ACTOR`, report text or a generic guard override. Ordinary report parsing and plain-note refresh are unchanged.
- `verifyValidationCheckpoint(evidence, {project, saved})` and `reconcileValidationCheckpoint({project, checkpoint, result})`: NEW typed consumers preserving S5's mechanical proof and ordinary completion payload/guards, with the additional once/producer bindings and reconciliation-before-CAS order. Existing `verifyTrainResult` requires `promotion-train/v1`, and current `reconcileBatchCompletion` can perform early CAS; neither is a drop-in reader of the new schema. Factor shared proof logic without broadening ordinary receipt acceptance.

These are proposed APIs, not available CLI flags or commands to execute. A later CLI surface must route to the same bounded native operations and cannot add an ordinary `skip-blockers`/`accept-substantive-delta` switch.
