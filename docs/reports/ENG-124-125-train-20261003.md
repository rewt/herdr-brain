The implementation is committed and ready for promotion-tier CI. ENG-124's recovery and ENG-130's log retention are covered by passing acceptance tests. ENG-125's operational train is implemented; its universal retry-count requirement needs a decision before the combined ask can be called fully accepted.

The first acceptance run failed against the previous implementation (eight failures, one pass). That evidence includes sandbox process-inspection refusals and bounded child timeouts, alongside the stale-main and lost-log-tail failures. Owned process inspection was then enabled for the offline fixtures. The final authored acceptance run passed all 18 tests in about 35 seconds; its complete TAP output is committed beside the initial red output. No model or live Herdr endpoint was used.

The tests establish:

- Main moving after a completed review, and while a reviewer runs, resumes with `--retry`; the completed review hash survives and no new worker run is created.
- Dirty or conflicting lanes retain their work and refuse automatic recovery.
- Settle invokes no suite, even with a configured command that would fail. Matching worker evidence preserves the entire log and its final TAP totals beyond eight KiB, and `lane check` itself flushes those totals to stdout.
- Three ready lanes stack in scratch and land with one promotion-tier execution. A lone lane runs one gate immediately. A matching green tree receipt is reused.
- With the last of three lanes broken, the other two land and the third remains available for correction within two extra executions. First- and second-position failures also land all good work, with tests allowing five total executions; those cases expose the universal cap discrepancy.
- Killing validation leaves main untouched and permits drain recovery after verifying and removing only stale fixture-owned locks. Killing the train after fast-forward recovers bookkeeping without repeating validation or integration.
- Changed queued heads, dirty lanes, STOP, scratch mutation and record supersession during validation prevent integration. Two authorized lanes sharing a record finish under one record lock.
- Bound promotions record the report timestamp, integration timestamp and elapsed seconds in queue results and a record CLI run note. Replayed authorization evidence rejects a forged source head.
- Disposable Git histories contain no merge commits or remotes. Production promotion never invokes push.

Existing settle, promotion and configuration assertions were migrated to review-only settlement and batch checkpoints. The offline release-case adapter now expects deferred validation instead of a settle-executed green gate. Those existing suites and the release harness were not run in this lane, following the operator brief; promotion runs the complete promotion tier once. Direct `lane promote`, legacy single-job recovery and the existing cleanup safety checks remain available. The bch-cloak settle-watch path, flags and behavior were untouched.

Self-review checked the implementation against the external brief: canonical Git ownership, clean original worktrees, exact captured heads, preserved replay trees, record readiness under lock, immediate queue snapshots, retained crash evidence and local fast-forwards. The train owns only its scratch work before integration; lane refs adopt a proved replay afterward through the existing locked compare-and-swap helper. Unexpected post-integration lane edits retain the lane with a warning.

Finish order: implementation committed, this report written and checked with the record CLI, report committed, then `node lanes/lane.mjs check` as the final action. The last check's tree-keyed receipt is retained by the lane validation module; no further lane work follows it.
