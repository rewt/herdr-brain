Herdr Brain: investigation and minimal design proposal

This is a research and design deliverable, not authorization to implement or activate it. The investigation began with AGENTS.md and docs/north-star.md and used implementation, retained receipts, event records, native session histories, installed CLI help/schema, and primary documentation. The final source/deployment check was at 2026-10-11 00:23 UTC, October 10 in the operator’s timezone. Herdr Brain’s record ended at event 4911; the examined BCH completion evidence reached event 15922. Live BCH work continued independently during the investigation.

No code, routing, permissions, release selection, monitor configuration, or BCH execution was changed. No additional workers, promotion gates, release preparation, or live acceptance were launched. Read-only measurements included receipt aggregation and a rendering experiment. BCH ownership remains with brain-bch-coordinator as coordinator and supervisor-opus as execution owner.

Herdr Brain already contains most of the execution machinery it needs. The smallest credible path is to adopt that machinery consistently, correct completion and recovery semantics, and give requests and delegated authority durable ownership. A session can supply a specialist service; its profile supplies behavior, Herdr and the harness supply control and addressing, and the associated record and artifacts supply continuity. A permanent reasoning supervisor and a separate network service for every role are unnecessary.

The reported inefficiencies have several causes: old defects that have remedies on main, deployment and configuration divergence, legacy paths that bypass those remedies, and a few remaining implementation gaps. Treating all of these as one missing orchestration system would replace working mechanisms and preserve the underlying ambiguity. This recommendation follows the repository’s dependency and ownership boundaries and its requirement that durability replace conversational memory without adding bureaucracy. [Repository instructions](/Users/rewt/development/rewt/herdr-brain/AGENTS.md), [North Star](/Users/rewt/development/rewt/herdr-brain/docs/north-star.md).

Several specific mechanisms explain why existing remedies only partly solved this:

- The cap controls how parsed lower-severity findings are handled. It does not authorize ignoring Major findings, FAIL results, unparsed severity, unresolved blockers or uncertain evidence. In the current decision code, automatic handling of deferred test evidence also requires PASS with no findings; PASS plus Minor findings, or capped findings plus test-only uncertainty, can still require supervisor judgment. Separate these two decisions without weakening either. Use typed findings and typed evidence obligations rather than making prose formatting determine whether another model is needed. [Review policy and decision code](/Users/rewt/development/rewt/herdr-brain/settle/settle.mjs:145).
- Settle commits the review document after the code under review. The implementation distinguishes the reviewed head and final review commit and can recover an uncertain review-commit response. Preserve that distinction in receipts. A review-document-only commit is not new code to review. A changed base, conflicting rebase, changed dependency or altered validation plan can change the evidence and must be assessed. Do not replace exact promotion validation with a loose patch-hash shortcut.
- Correction briefs should resolve identified findings and their required evidence. Newly discovered optional improvements should be linked follow-ups, not extra scope added to a lane that already has acceptance evidence. ENG-1116 illustrates the cost of allowing those scopes to accumulate.
- BCH’s automatic review initially treated some design-only work as code inherited in a lane, producing wrong-subject reviews. Its later `DESIGN ONLY` guard is an existing remedy, but a typed requested artifact is more reliable than a phrase in a brief. [BCH auto-review guard](/Users/rewt/development/bastian/bch-cloak/.lane/supervisor/auto-review.sh).
- Release notes show full pre-runs before candidate preparation as well as focused checks on later changes. Candidate preparation already owns the full offline release suites. Move the full run to the immutable candidate boundary once; retain focused development checks and required release acceptance. Do not add a second full pre-cut qualification stage.

Actual batch formation does not support a blanket conclusion that configuration split the queue. The retained native train receipts contain 106 completed batches: 90 singles, eight pairs, six triples, one four-member batch and one five-member batch. All 133 original job memberships had the same recorded compatibility key: lane CLI, explicit validation override, lane configuration and workflow mode. That does not establish that every pair would merge cleanly, but it rules out different values of those keys as the explanation for these singleton batches.

Of 64 plans with usable enqueue and start clocks, three had a compatible job apparently queued before the recorded batch start but outside its membership. Two were within 12–18 milliseconds; another was about 89 seconds earlier on older timing semantics. Membership selection can precede the recorded start, so these are not proof of a queue bug. At the other 61 starts, no additional already-enqueued compatible sibling was visible from those timestamps. We do not have reliable “became ready” timestamps for work that callers had not yet enqueued. Consequently the retained data cannot distinguish all lost batching opportunities from genuinely sparse readiness.

BCH provides a concrete adoption example: its owners identified three compatible, disjoint pieces of ready work on October 10 and formed the successful harness/docs/fees batch. The generic native queue did not form it; the local supervisor did. Prefer enqueueing the compatible ready set together at a natural completion boundary. If current per-job enqueue/worker-start races prevent that, add an atomic enqueue-many operation retaining each member’s binding. There is no demonstrated need for an arbitrary waiting window or a new batching service. [Promotion implementation](/Users/rewt/development/rewt/herdr-brain/promote/promote.mjs:351), [batch policy](/Users/rewt/development/rewt/herdr-brain/promote/README.md).

Keep compare-and-check protection for included items, current runs, authority, blockers and accepted reports. Historical exclusions must remain fully accounted for, but an unrelated excluded item advancing should not force a stale update to that item or prevent closure of unchanged included members. The proposed communication contract should be small enough to use through existing CLI or MCP operations. Organizational facts belong in the record, written only by the record CLI; transport attempt details can remain in the existing supervisor journal. Those stores have different responsibilities and share request/effect identities.

| Required field | Meaning |
| --- | --- |
| Contract version, request ID, message ID, correlation/parent ID | A stable assignment identity, unique delivery/update identity, and relationship to the initiating work or question. |
| Canonical project and record identity | Bind to the Git common directory and associated record, not a basename or workspace label. |
| Sender and recipient | Authorized role/principal plus verified endpoint binding; include exact native session/generation when addressing an incarnation, or an explicitly assignable role when requesting replacement-capable service. |
| Intent | Answer, investigate, recommend, decide within a grant, execute authorized work, review, or report. It is not inferred from a free-text imperative alone. |
| Expected output and acceptance | Answer, artifact, review, code change, decision or status; scope, evidence requirements and accepting role. |
| Evidence references | Relevant record IDs, artifact paths and hashes, commits/trees, base assumptions and prior answers. Pass references and small excerpts, not the organization’s transcript. |
| Authority reference | An independently checkable operator grant or decision, allowed actions, scope and exclusions. A claimed sender or personality name is not authority. |
| Ownership and continuation | Accountable role, accepted claim/lease, next action, escalation or expiry condition, and bounded referral policy. |
| Result or failure | Result artifact/answer references, whether it is advice or an authorized decision, residual uncertainty, failure category, retry safety and next owner/action. |

Transport acknowledgement means that the message was durably recorded. Recipient acceptance means that the request has an accountable claimed owner. A result means that output exists. Acceptance means the output met the requested contract. These are different events; native idle/done or process exit establishes none of the later ones by itself.

Deduplicate by request/effect ID and payload hash. The same ID with the same payload returns the existing receipt; the same ID with different content refuses. A lost transport acknowledgement is resolved by reading the durable request and retained native evidence before resubmission. Resend the same identity where delivery is uncertain; never turn uncertainty into a fresh assignment or promotion. Critical mutations remain guarded and idempotent at the CLI, since exactly-once network or terminal delivery is not a reasonable assumption.

Claim changes require a record-lock transaction. A replacement session does not inherit a session-addressed request silently. Record explicit reassignment, validate the new endpoint and revoke or fence the old claim before it can perform consequential effects. Role-addressed work may transfer under its grant, but session-addressed messages fail with a replacement/unavailable result until the owner chooses a next step. This supplements existing notice IDs, action receipts and lifecycle checks; it does not replace them.

Reusable personalities need a purpose, model and reasoning configuration, permitted action classes, expected inputs, output obligations, stopping conditions and a version. Existing route and native profile facilities already supply part of this. Keep behavior configuration separate from live endpoint bindings and from authority grants. Starting a profile called “architect” must not confer architectural decision rights by itself.

An engineer’s architectural question can then complete without routine human mediation:

1. In an already-authorized lane, the engineer encounters an ambiguity about whether a cache key must include schema version. It records a question against that work, with the affected commit, relevant interfaces, options, desired answer and its existing scope grant. It does not open a second engineering lane.
2. Deterministic lookup checks applicable decisions, lessons and prior answered requests. If a current decision already resolves the question, return it with its evidence and applicability conditions. A stale decision is not silently reused after its assumptions change.
3. If judgment remains necessary, the role registry selects the responsible architect for that project/domain. Prefer an appropriate available session with the required permissions; otherwise the dispatcher may start one bounded architect session if the standing grant permits it.
4. The architect accepts ownership, receives a compact brief and reads deeper evidence only as needed. It returns an answer with rationale, confidence and references. It marks a recommendation as a recommendation; it records a binding decision only if the referenced grant delegates that decision.
5. The engineer receives the correlated result and resumes within the original scope. It records the applied answer and commit reference. The architect’s session can exit immediately after its output and next action are durable.
6. If the answer would introduce a compatibility break or operator preference outside the grant, the architect records that unresolved decision with substantive options and consequences. It does not pretend that technical expertise authorizes the change.
7. If specialists disagree, the owning role requests one bounded adjudication on the precise disagreement and existing evidence. Do not send the whole problem around the organization or restart completed research. Unresolved uncertainty is a result that can block the affected action while independent work continues.
8. The requesting workflow retains accountability until the specialist accepts the handoff; afterward the specialist owes a result or explicit failure. Unavailable recipients, expired claims and failed delivery return to that accountable role through the deterministic dispatcher. Referral limits and a next-action record prevent mutually abandoned questions.

Supervision remains a responsibility, while its reasoning sessions become disposable. Routine report intake, duplicate suppression, applicability checks, known severity policy, queue admission, lock acquisition, gate tracking, receipt reconciliation, dependency wakeups and safe cleanup are deterministic operations. Source autopilot, notice journals, watchers, promotion receipts and housekeeping already implement substantial parts of these. Scope interpretation, conflicting evidence, genuine architectural choices, unexpected failures and reserved decisions require reasoning.

For those exceptions, start or resume an authorized bounded role session with only the relevant work, evidence, grant and requested decision. It records its judgment and next action and finishes. Never keep a model alive merely to poll, acknowledge notices or remember who should act. The disabled entry integration can remain disabled; explicit native launches and the existing foreground tools remain viable.

The smallest remaining continuity gap is an owned request/claim and role-wakeup adapter. Extend existing supervisor delivery machinery so durable eligible work can wake a permitted role when no reasoning session exists. Use Herdr events and native lifecycle facilities; perform a durable rescan on adapter/plugin restart and timed recovery only for recorded deadlines or missing events. Reuse one project/fleet event runner, not a service per specialist. The existing inbox already survives sender exit and can restart its worker; it currently waits for a named recipient rather than generally instantiating and claiming the right role.

There must be an identified non-model process responsible for pending delivery while all reasoning sessions are closed. If that process crashes, a supported plugin or OS lifecycle owner must restart it and replay the durable queue. If the whole machine is stopped, continuation begins at the next supported startup. Sockets and personality files alone cannot supply this guarantee. The core remains foreground, dependency-free and model-free; harness branching stays in adapters.
