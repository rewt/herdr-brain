## Findings
- [Moderate] promote/promote.mjs:321 - With the policy at its default (off), every project now has a new cross-process retirement owner lock with a 1 s wait, and it is claimed outside the existing error handling. Housekeeping holds that claim for its whole tick, sweep included (deadline up to 720 s). If a promotion's \`finishCleanup\` collides with it, \`locked:\` escapes the legacy try block. \`perform\` then returns \`post-promotion bookkeeping failed ... lane kept for inspection\` with no \`cleanup.state: pending\`, so \`retryCleanup\` never retries it. On the resume path the failure is mislabelled \`integration checkpoint cannot be verified\`, and inside \`retryCleanupLocked\` it aborts the loop for the remaining rows. That is a lane-closeout regression for default-off projects such as BCH; Fix: claim the owner lock inside the legacy try, so contention becomes an ordinary \`cleanup.state: pending\` row with its existing retry and backoff (or wait for the claim under the cleanup deadline), and add a default-off contention fixture.
- [Moderate] housekeeping/housekeeping.mjs:91 - With the policy off, \`tidyFinishedTabs\` and \`tick\` (line 143) call \`claimRetirementOwner(..., { waitMs: 1000 })\` (and \`closeoutPolicy\`) before any try block. If promotion legacy cleanup or a manual \`retire.mjs sweep\` holds the claim for more than a second, the main-loop iteration throws. That skips the tidy pass, \`resumeInbox\`, interrupted-worker resume, notices and summary publication for that tick, which breaks the existing promise that a failed tidy never stops recovery; Fix: on owner-lock contention, log a \`retirement-skipped\` (contended) row and skip only the retirement-owned steps, so resume, inbox, notices and summary publication still run; add a housekeeping fixture holding the claim.
- [Moderate] promote/promote.mjs:428 - With the policy on, \`consumeRequests\` runs at every promotion drain start (empty queue) and in its finally block. Each time it appends one \`closeout.retry\` record event per distinct topic among all \`landed\` entries ever written. Entries are never removed (\`lib/closeout.mjs\` has no prune path), and the filter does not skip completed or unrelated entries. Every promotion therefore grows the record by O(history) events, and wakes every old deferred entry, each re-evaluation adding a \`closeout.evaluated\` receipt. This is the churn and rescanning the operator ruled out, and it grows record and fold cost without bound; Fix: retry only the landed entries bound to the jobs that drain just completed, and only if their latest evaluation is deferred on \`lifecycle-lock-released\`; skip completed entries; retire or compact completed entries, so \`readCloseoutEntries\` does not rescan all history on every enqueue.
- [Minor] lanes/lane.mjs:2354 - \`review.verdict\` always records \`followup\_expected: false\`. Neither \`lane review\` nor settle offers any way to declare an expected same-session follow-up. The retention path (\`lib/retire.mjs:254\`, \`endReviewFollowup\`) and the operator's "whether a same-session follow-up is expected" field are therefore reachable only from fixtures; Fix: add an explicit, validated option, for example \`lane review --followup-expected\` passed through \`recordReviewVerdict\` and settle's \`recordCompletedReview\`, or document that follow-up declaration is out of scope and file it as a follow-up item.
- [Minor] lib/closeout.mjs:268 - \`readyLane\` runs \`git symbolic-ref --short HEAD\` (via a throwing \`execFileSync\`) on every recorded run's existing workspace. One recorded workspace with a detached HEAD, or one that is not a Git checkout, makes the optional \`lane ready \<topic\>\` fail for unrelated lanes, even though the new worker brief tells agents to run it as their last step; Fix: filter to runs whose workspace's Git common directory matches the project, and treat a symbolic-ref failure on an unrelated run as no match rather than an error.
- [Minor] lib/closeout.mjs:252 - With the policy on, an ingested \`outcome: done\` report for a run whose workspace is the canonical checkout or not a linked lane (desk, supervisor and planning runs) records \`closeout\_binding\_errors\` on the source event. It also prints \`has no durable target binding; kept; use named supervisor recovery\` on every such ingest, so routine non-lane completions look like closeout failures that need recovery; Fix: in \`signalTargets\` and \`bindEntry\`, treat a run without a registered linked lane worktree as not applicable (no error field, no stderr), and keep the binding-error path for real lane targets.
