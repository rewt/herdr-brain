## Findings
- [Moderate] dispatch/dispatch.mjs:190 - The new memory wait is unbounded and ignores supervisor STOP: settle checks STOP in correctionStopped and then invokes dispatch, which can now sit in waitForMemory for hours and launch a correction worker as soon as pressure clears even if the operator placed STOP during the wait; the same applies to the worker-stage wait at dispatch/dispatch.mjs:247, and the check hook added to waitForMemory is exercised only by a unit test and passed by no caller; Fix: pass a check callback from dispatch (both stages) that stops with the existing resumable stopped result when .lane/supervisor/STOP exists in the repository, and add an offline test that creates STOP during a simulated pressure wait and asserts no lane open or worker launch.
- [Moderate] lib/memory.mjs:52 - Any nonzero current swap use defers work with no deadline, but on Linux cold swapped pages stay counted in SwapTotal minus SwapFree long after pressure ends (and macOS swap files shrink only slowly), so an otherwise idle host with a few MiB of stale swap holds dispatch, settle reviews and promotions in an indefinite wait, which in practice refuses work rather than deferring it until pressure clears; Fix: treat swap as pressure only when it is significant or active, for example swap use above a fraction of RAM combined with low available memory, or a change in swap use or swap-in or swap-out counters between consecutive samples, and add a test showing stale idle swap with ample available memory does not block.
- [Minor] lanes/lane.mjs:2254 - The second wait runs after validation while the project promotion lock is held, so pressure caused by unrelated processes blocks the cheap fast-forward, every queued promotion and release indefinitely, and this path has no test; Fix: drop the pre-fast-forward memory wait (the expensive validation step is already gated before the lock) or perform it before acquiring the lock, and cover whichever behaviour remains with an offline test.
- [Minor] lib/memory.mjs:46 - On macOS a vm\_stat failure falls back to os.freemem, which reports only free pages and excludes inactive and speculative pages, so the fallback can invent low-memory pressure and cause an indefinite wait, contrary to the release comment that a missing probe never invents a pressure signal; Fix: on darwin treat a failed vm\_stat as unknown available memory (advisory only, no low-memory reason) or document and test the fallback as conservative.
