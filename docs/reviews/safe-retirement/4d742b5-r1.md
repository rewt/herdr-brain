- [Minor] lib/retire-trigger.mjs:43 - A consume deadline that expires during the final candidate's re-observation is swallowed by observe's diagnostic try/catch blocks (watcher-callback and callback-receipt owner lookups turn RETIREMENT\_DEADLINE into an unknown reference or process\_gone false), so executeRetirement records a skip-close instead of deferred, no later deadline check runs, and consumeRetirement writes handled.json for that revision; the hint is consumed and the tab stays retained until an unrelated later hint, contrary to the report claim that a deadline always leaves the hint pending; Fix: after adapter.apply returns, treat Date.now() at or past the deadline (or any diagnostic produced by a deadline error) as pending and return without writing handled.json, and add a fixture whose last re-observation crosses the deadline inside an owner lookup
- [Minor] promote/promote.mjs:477 - Moving the start-of-drain catch-up after the acknowledgment also moves it after the dequeue checkpoint: a newly dequeued single (non-batch) job is already persisted as current in phase promoting while consumeRequests runs an unbounded full observation and guarded closes, so a worker crash or kill during catch-up makes the next drain report it as interrupted (previous worker stopped in promoting; explicit re-enqueue required) where previously the job would still have been pending; Fix: when the acknowledging iteration dequeued a job, defer the start-of-drain catch-up until that job's result is persisted (the finally block and per-job cleanup already run it), or run it only when entry is null, keeping the acknowledgment first
- [Minor] supervisor/retire.mjs:305 - pruneReceipt calls fs.unlinkSync after a non-atomic read, so two concurrent applies (housekeeping tick, tidy, promote cleanup or consume, which share no apply lock) that both observe the same absent receipt make the second unlink throw ENOENT, aborting that whole apply before any close; and any pruning error raised inside the close callback after a successful \`tab close\` is recorded by executeRetirement as close-failed for a tab that was actually closed; Fix: ignore ENOENT in pruneReceipt and make post-close receipt pruning a logged diagnostic that cannot change the closed result, with a fixture where the receipt disappears between observation and pruning
