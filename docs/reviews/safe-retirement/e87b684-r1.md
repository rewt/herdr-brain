## Findings
- [Moderate] lib/retire-trigger.mjs:29 - consumeRetirement holds retirement/consume.lock across a project-wide plan plus guarded apply (each apply candidate re-observes the whole project), but acquireLock has no stale-owner recovery and canonical supervisor entry runs \`retire.mjs consume\` with an 11 second cap and killSignal SIGKILL; a consume that is killed mid-apply leaves the lock directory behind, after which every later entry and every promote-drain catch-up fails immediately with \`locked\`, so the new trigger consumer stops acting permanently until someone removes the lock by hand (inspectEntryLocks does not even list retirement locks); Fix: make the retirement request and consume locks owner-aware (record pid and birth identity, reclaim only when ownerAlive proves the owner gone) or have entry run consume without SIGKILL under a bounded per-candidate budget, add the retirement locks to inspectEntryLocks, and add a test where a stale consume.lock from a dead owner is reclaimed and a live owner is respected
- [Moderate] promote/promote.mjs:404 - The start-of-drain consumeRequests call runs before the worker sends its ready acknowledgment, and start() fails the enqueuing \`promote TOPIC\` command with \`worker startup unconfirmed\` after the loadTimeout of 5 seconds; whenever a hint is pending (any ingest, disposition or reconciliation since the last drain) the worker first performs a full Herdr, Git and process observation of every project workspace and then guarded closes with a fresh full observation per candidate, so on a host with dozens of tabs the promote command can report failure while the worker continues; Fix: send the ready acknowledgment before the start-of-drain retirement catch-up (or run that catch-up after the first acknowledgment), and add a drain test with a pending hint that asserts the acknowledgment precedes retirement observation
- [Minor] supervisor/retire.mjs:227 - retirement-occupant/v1 receipts are written per tab at every watcher and settle/executive/plan launch but are never removed, and every observation (housekeeping ticks, tidy, consume, and each executor re-observe) calls readOwner, which spawns the native process helper once per receipt in this project; the receipt directory and per-observation process spawns grow without bound over the project lifetime, steadily slowing retirement and the bounded entry call; Fix: delete a receipt after its tab is closed or once its tab is absent from the current Herdr inventory, and skip readOwner for receipts whose tab is not in the observed tab list, with a test covering receipt pruning
- [Minor] contrib/settle-watch.mjs:219 - The watcher launch receipt is recorded whenever HERDR\_TAB\_ID and HERDR\_PANE\_ID are set, not only when the watcher owns its tab via --spawn or --close-tab-on-exit; a watcher run in the foreground of an operator's ordinary shell tab in the canonical checkout leaves a receipt, and once the watcher exits the planner bypasses the canonical/desk workspace keep rules for that callback tab and tidy, housekeeping or consume will close the operator's idle unfocused shell tab; Fix: write the watcher receipt only when --close-tab-on-exit is set (the --spawn path always appends it), and add a fixture where a watcher without that flag leaves its tab kept
