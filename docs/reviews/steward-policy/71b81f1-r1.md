## Findings
- [Major] discovery/native-sandbox.mjs:284 - Claude launches replace the per-launch command PermissionRequest hook with a loopback HTTP hook served from the adapter process, and Claude treats HTTP connection failures, non-2xx replies and timeouts as non-blocking hook errors that fall through to the interactive permission dialog; if the adapter dies or is killed while Claude keeps running in the pane (the native child shares the terminal and is not bound to the adapter lifetime) or the adapter event loop is held past the 15 second hook timeout by the synchronous git, lock and fsync work in handlePermission, the request shows the dialog and reproduces the unattended overnight block, and nothing in the diff shows HTTP is required because the command hook carries the identical protocol and the launcher tests already run on it; Fix: register only the per-launch command hook for Claude and remove servePermissionHook, the settings rewrite and the launch.ready wait, or if HTTP is kept retain the command hook as the decision path and add a test proving a dead or stalled listener still yields a deny.
- [Moderate] supervisor/permission-hook.mjs:2 - The command hook statically imports permission-hooks.mjs and its whole dependency graph before its try block and parses the launch binding outside handlePermission, so a module load failure (for example a checkout mid-rebase or a removed file) exits nonzero with no decision, which Claude treats as a non-blocking error and answers with the dialog, and a missing or malformed binding is denied without any audit receipt despite the every-decision-audited requirement; Fix: load dependencies with dynamic import inside the try, on any uncaught failure print the deny JSON and exit with code 2 with the nudge on stderr, pass an unparsable binding into handlePermission as null so the denial is audited, and add tests for an unloadable module and an absent binding variable.
- [Moderate] brain/lib/permission-policy.mjs:25 - The funds, publishing and permission-expansion keyword patterns run over the tool name plus raw tool input, so a Claude Read of an in-project file whose path contains release, push, deploy, publish, trust or transfer (this repository has many, such as the release acceptance reports and the codex hook trust brief under docs) is classified as a never-list request, denied although the approved policy allows project reads, and pages the operator by iMessage; Fix: for Read requests rely on the resolved-target credential check and project containment only, apply the funds, publishing and expansion keyword classes to command-bearing or non-read tool inputs, and add a test that an in-project release report read is allowed without an alert.
- [Minor] brain/lib/permission-audit.mjs:11 - The permission audit takes its lock with zero wait, so two hooks auditing at the same instant (two sessions, or parallel tool calls in one session) make the second throw and return the audit-unavailable denial, declining an approvable read and pushing the session to record a needless question; Fix: pass a small bounded waitMs such as 2000 to noticeLock (safe once decisions run in per-request command hooks rather than a shared event loop) and add a concurrent-audit test.
