# Release within the project's mandate

Read the active project's release instructions and assigned release record before
choosing commands. Establish the canonical project, release coordinator, exact
candidate, runtime, existing attempt and authority for each requested effect.
Loading this skill grants no release, activation, pin change, adoption, publication,
funds or secret authority. A worker hands evidence to the existing coordinator.

Use one full final-release coverage obligation shared by the fixes. Preserve valid
completed coverage bound to source, runner, environment and dependencies; after
corrections run only failing, actually affected or unrun controls. Preserve file
groups and limits. No green replay, worker-wide release tier or reviewer suite.
A changed validity input requires an explicit coverage disposition, not an invented
green aggregate or automatic reuse of stale evidence.

For Brain routine runtime updates, the authorized supervisor uses
`herdr/release.sh build TAG --landing-checks` or `ship TAG --landing-checks`.
These ship on landing checks, explicitly record full coverage and per-candidate
live acceptance as UNRUN, and retain snapshot/sealing, identity, activation,
installed-launcher checks, rollback and pin guards. They cannot qualify for stable
adoption; do not add a full-suite or native acceptance gate to each internal update.
Repeated per-candidate live runs would recreate the removed routine gate.
This Brain choice does not change BCH's own release procedure or authority.

Before a stable release that BCH adopts, resolve all Major correction obligations
with their specific checks. One full offline coverage obligation, actual live
acceptance of the exact stable candidate, package sealing and installed-consumer
readback must support the stable activation/adoption decision. Brain's
`build TAG --live` retains this path and the existing coverage continuations.
Source inspection or a successful offline build alone cannot establish live
acceptance. Keep failed, interrupted and UNKNOWN attempts and their evidence.

For Brain, consult the canonical `herdr/README.md`, `herdr/RELEASE-PINS.md` and
`acceptance/README.md` when the assigned stage needs them. The existing
`herdr/release.sh` owns build/ship/activation mechanics; only the canonical
supervisor releases. Do not restart services/watchers or edit pins/saved runtimes
as incidental troubleshooting. BCH uses its own release procedure and identity;
shared skills do not adopt Brain tooling or execute a BCH pin change.

Follow the record's current ordering and holds. Rehearsal publication remains
PRIVATE with its actual fresh-clone pre/post checks. Public release, funds, keys,
trust anchors and adoption retain their action-bound checks. Route missing or
reserved authority to the PROJECT SUPERVISOR; a native refusal stops that effect.

Report exact candidate, carried/fresh/unrun coverage, acceptance and consumer
receipts, correction dispositions and remaining authority decisions in the owning
record. Use the existing completion path; do not add a parallel release scheduler,
monitor, approval gate or claim that handing off evidence activated a release.
