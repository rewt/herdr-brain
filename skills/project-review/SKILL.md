# Review the captured change

Start from the assigned review record, original acceptance, immutable base/head,
captured diff and producer report/evidence. Use the active project's instructions,
identity and existing review schema. The source owner's later HEAD or a missing
worktree does not change the captured target; read commit objects and retained
evidence. A writable source worktree is unnecessary for this review.

The existing line creates and dispatches one async post-code review per delivered
source item/head, cap1. Use its assigned independent reviewer route, including
the project's configured other-family route where applicable. Never create an
extra plan review, concurrence stage, reviewer, watcher or replacement UNKNOWN
attempt. The approximately 30-minute target is advisory. Landing proceeds
independently of the verdict.

Build, test, prepare, install and probe/check executions are zero. Inspect source,
diff and retained producer evidence read-only. Reuse the designated producer's
routine verification once; distinguish inherited evidence, independently observed
facts and unsupported claims. Report a missing functional requirement specifically,
not as generic uncertainty because you did not repeat a producer command.

Assess the delivered result against the original intent and actual authority,
using the complete report/evidence when its summary is truncated. Identify what
the evidence establishes, missing or unrun proof, and who owns the next action.
Keep useful cold-reader observations in this same review report; the summary is
an assertion to assess, not its own acceptance. No additional review is needed.

Follow the assigned output schema exactly, including required inherited-gate
acknowledgments and an empty re-executed list. A PASS is a review verdict, never a
claim that you ran tests. Make findings actionable: concrete trigger, changed code,
observable consequence, severity and the evidence or correction needed. Preserve
known failures and historical verdicts. Do not edit or fix the producer's source.

For Brain's running-line Minor batching (ENG-1352), when there is at least one
Minor and no Major, set `verdict: PASS` and record every Minor under exactly
`## Batched Minors`, one `- path:line - explanation` bullet per finding. Keep each
finding on one physical line, with its trigger and consequence. Omit frontmatter
severity findings, tagged `[Minor]` bullets and engineer proposals in this case:
the sealed intake interprets those as immediate corrections. This project rule
overrides the older generated brief's Minor format. Keep inherited checks and
acceptance declarations accurate; unproven outcome evidence stays unproven.
When a Major exists, use the original schema for all findings and retain Major
correction checks. Other projects keep their own review format.

The immutable report is the finding source. Brain's
`measurement/minor-batches.mjs` lists these Minors and recorded dispositions; see
`measurement/MINOR-BATCHES.md`. Do not file an individual engineer proposal for
these batched Minors. An owner-chosen related batch uses ordinary engineering and
its one independent diff review, rather than a linked correction with no review.

Return through the existing assigned report/prompt delivery and exit. The record
links at most one formal correction round; later findings fix forward without a
second full review. Majors need actual specific correction checks before final
release. A correction is owned by its assigned engineer, not an unowned verdict.
Do not invoke supervisor cycle mutations or keep a session waiting for a callback.

Source/record/identity contradictions and unsafe or native refusals go to the
recorded PROJECT SUPERVISOR with retained evidence. Stop only the affected effect;
never borrow authority, replace an existing attempt or turn a routine technical
question into an operator-reserved decision.
